# Optional parallel downloads to the browser machine

The user clarified that Download to the local machine was slow, rather than in-view PDF/media loading. Existing controls handed a single URL to the browser and did not schedule parallel ranges. This identifies the existing mechanism, not a measured cause of the reported network speed. The user also asked whether parallel transfer should be optional and whether browsers support in-memory PDF: ordinary download remains available, while native PDF viewing remains unchanged.

The shared provider owns the browser download helper, advertised configurable range policy and stat-based version preconditions. Supported secure-context browsers choose a destination from the original click, fetch four 1 MiB ranges by default, serialize positioned temporary writes and commit after final metadata verification. Failed ranges retry within configured bounds; failure/cancellation aborts pending writes. The metadata fingerprint is not a content digest or filesystem snapshot. Unsupported direct-writing browsers retain native handoff without a whole-file JavaScript buffer.

Viewer offers Parallel download, Ordinary download and cancellation/progress. The browser PDF toolbar still uses native download. Manager uses the shared helper and shows black progress below the path; Shift-click explicitly selects ordinary download. Tree navigation/superseding operations cancel its custom transfer. STATE and package references carry the reusable installation guidance.

Built user-files, viewer and manager with their existing build scripts against DSH_CHECKOUT=/root/deepseek-harness; all completed successfully. The first provider build identified its new policy module missing from the explicit Client file list; that list was corrected before successful builds. One lightweight agent inspected only chunk allocation, writer lifecycle and picker activation. No tests or browser automation ran, and no worktree was created. Browser download speed and actual save-picker behavior remain for user observation.

Both consumers and the provider were already linked into the Web profile. Bundle membership, profile configuration, proxy configuration and official Harness source were unchanged. Restarted dsh-web under existing activation authorization; the service was active and the Web homepage returned HTTP 200. Startup is not evidence of client throughput or completed local-file download.
